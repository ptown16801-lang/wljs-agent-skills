# W5 fix: `FailedAssertions` reports 0 after a plain call (Oct 22, 2026)

File: `~/.local/share/wolfram-agent-skills/agenttools/744d2d1.../wolfram-debugging/scripts/WolframDebugging.wl`
(backup `WolframDebugging.wl.orig-2026-10-22`). Patch: `patches/W5-failedassertions.diff`. Evidence scripts and
outputs: `fixes/scratch-W5/` (`e1`-`e4.wls/.out`, `extra.wls`, `suite-*.json/.log`). All runs: fresh WL 15.0 kernel,
`bwrap --unshare-net`, `$AllowInternet = False`.

## Mechanism
Not a `Block` or helper bug. It is the evaluator's "already evaluated" mark on expression nodes, plus how
`Assert` behaves when Off:

- With `Off[Assert]` and no `"Assertions"` handler, `Assert[test]` evaluates to itself, unevaluated
  (`Assert[False]` gives `Assert[False]`), and the test is not evaluated (a side-effect counter `k` stays the same
  in plain calls).
- After one plain call, `Assert` is not called at all, even with the handler active: the side-effect counter in the
  test stays the same under the handler too (`e3`), and the count is 0. So the node is skipped as already
  evaluated. While a handler is active nothing is marked: two handler calls in a row both count 1 (`e2`).
- The mark sits on the stored expression node. A node is shared between calls when substituting the arguments leaves
  it unchanged. So the bug is not specific to `Block`: `g3[x_] := (Assert[$z > 5]; x)` (no `Block`) is affected,
  while `Assert[x > 5]` (it contains the pattern variable), `With` and `Module` (they rename or substitute, making a
  new copy) are not (`e3`, `e4`). `DownValues[f] = DownValues[f]` keeps the stale state (same node); a
  `Compress`/`Uncompress` copy or re-`Get` makes new nodes and clears it (`e2`).
- The mark depends on `Assert`'s own symbol timestamp. It is cleared by `Update[Assert]`, `Update[]`, `On`/`Off[Assert]`
  (even `Off` when already Off) and changing `$AssertFunction`. It is not cleared by `ClearSystemCache[]`,
  `Update[f]`, or changing a symbol in the test (`$z = 2`) (`e2`-`e4`).
- The kernel's internal flag cannot be inspected directly. The "evaluated mark" explanation is inferred from this
  behaviour, but every observation fits it.

## Change
In `FailedAssertions`, call `Update @ Assert;` right before the `Internal`HandlerBlock` (with a comment). This
invalidates the stale marks, so every `Assert` in `expr` is reached by the handler. Nothing is left changed: the
On/Off state of `Assert`, `$AssertFunction` and the handler list are the same before and after (checked). The only
effect is that cached "evaluated" marks involving `Assert` are dropped, the same thing `Off[Assert]` already does.

## Limits
- The suite has no test for this case (its `FailedAssertions` test uses a fresh definition), so the regression is
  covered only by the scripts above. Wolfram's suite was not changed.
- Plain calls still mark the node after `FailedAssertions` returns. That is harmless, because each call clears the
  marks first. Code that evaluates outside the handler's dynamic extent (another kernel, a scheduled task, a
  parallel subkernel) is not covered, as before the fix.
- `Update[Assert]` costs a re-evaluation of `Assert` nodes that were marked as evaluated; this is negligible.
- The workaround in BUGS.md (call `FailedAssertions` right after reloading) is no longer needed with the patch.
