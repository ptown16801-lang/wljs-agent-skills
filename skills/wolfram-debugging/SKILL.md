## On WLJS
- The upstream "MCP server (preferred)" and "bundled scripts" sections are replaced by the routes in ROUTES.md. Do not run the pristine `scripts/*.wls`: each calls `PacletInstall`.
- Upstream assumes a persistent MCP kernel for stateful work: on this computer that is the WLJS kernel, through WLJS's MCP tools (`mcp__wljs__kernel_evaluate`, or notebook cells with `mcp__wljs__add_cells_batch` + `mcp__wljs__evaluate_cell`) or `wljs eval`. A fresh, network-blocked kernel is `wolfram-direct`.
- **`FailedAssertions` right after loading** (bug W5 in tests/bugs/BUGS.md): with assertions Off, after one plain call of a function with a `Block` body the helper reports 0 failures until the definitions are reloaded; call it right after `Get`, or reload first.
- **Use the helpers, and leave global state alone** (Level C, Oct 22: a run diagnosed an `Assert` failure by turning `On[Assert]` globally in the shared kernel and never used the helpers). For assertions call `WolframDebugging`FailedAssertions[expr]` (works with Assert off; gives the line, file and caller); for messages `WolframDebugging`CollectMessages[expr]`. Never toggle `On`/`Off`, `$AssertFunction` or other global settings in the shared WLJS kernel; use `Block` or a fresh kernel.
- Environment for the upstream "where does the code run?" table: the WLJS kernel reports `$EvaluationEnvironment` = "Session", `Global` context, and `Trace` works (tested). It is a shared, persistent kernel: follow upstream rule 7 (scope every change).
- Load the helpers once per WLJS session: `wljs eval 'Get["~/.local/share/wolfram-agent-skills/agenttools/744d2d154871adcd2cec2ebfcf30a5eb8f65b8dd/wolfram-debugging/scripts/WolframDebugging.wl"]'`, then call e.g. `wljs eval 'WolframDebugging`CollectMessages[expr]'` (tested).
- Reproduce autoloading or package-loading problems in a fresh kernel (wolfram-direct), as upstream rule 8 says.
